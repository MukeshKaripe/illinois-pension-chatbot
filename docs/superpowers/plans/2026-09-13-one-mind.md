# One Mind Implementation Plan (Phase 3a)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One model reads the question, searches the Code, reads what came back, searches again if it has to, and writes the answer out of the same conversation — instead of a pipeline writing queries before it has seen any statute and a second model narrating the result.

**Architecture:** A ReAct loop behind `agent_mode`, with the four retrieval tools. `triage` and `decline` are untouched in front of it; `guardrails.verify` is untouched behind it. The loop's message history continues straight into the streamed answer — no second call to a model that was not there. The pipeline stays exactly as it is and remains the default.

**Tech Stack:** Python 3.12, `uv`, pytest (`asyncio_mode = "auto"`), Azure OpenAI `gpt-5.6-luna-1`, LangGraph, ruff, mypy.

**Spec:** `docs/superpowers/specs/2026-09-12-intelligent-agent-design.md` (§2, "Architecture: one mind, one history")

## Global Constraints

- Backend commands under `uv`. Unit tests must not touch the network — the loop's tests fake `call_with_tools` and the tool bodies.
- `uv run ruff check .` reports **37 pre-existing errors**. Add none. Ruff earns its keep here: it caught an undefined name in Phase 2b that no test reached.
- **The pipeline is the default and must not change.** Every existing eval and test runs against it unchanged; a diff that touches pipeline behaviour is out of scope.
- **Tools write the state keys the pipeline already writes** — `retrieved_sections` above all. That is what lets `prepare_answer`'s style half, `guardrails`, `card.py`, the SSE layer and the whole frontend stay untouched.
- Latency is **not** a constraint (spec §2). Loop iterations may use real reasoning effort.

### Verified before writing this plan

Three facts that the architecture depends on, checked against the live
deployment rather than assumed:

1. **`gpt-5.6-luna-1` supports tool calling**, at `reasoning_effort: "none"`.
   A `search_statute` schema came back as `finish_reason: tool_calls` with
   sensible arguments.
2. **A full round trip closes.** Feeding a `role: "tool"` result back produced
   `finish_reason: stop` and an answer citing `[40 ILCS 5/11-134]` from the
   supplied text — two steps, no coaxing.
3. **The answer path is already a stream over a message list**
   (`graph.py:355-375`), so continuing the loop's history into it is a change of
   what `messages` holds, not a new mechanism.

### Scope: retrieval first, calculation second

This plan builds the loop and gives it the **four retrieval tools**. It does not
give it coverage or calculation. That split is deliberate: a loop with
`search_statute` is a complete, measurable thing — it should flip the two
baseline cases that are purely about giving up too early — while `compute_benefit`
drags in coverage, recipes, inputs and the stand-in question all at once.

**Phase 3b** adds `check_coverage`, `lookup_recipes` / `derive_recipe` and
`compute_benefit`, and targets L01, L03, L05 and L08.

What 3a targets, from `docs/superpowers/baselines/2026-09-13-pipeline.json`:

| Case | What the pipeline does | What the loop must do |
|---|---|---|
| **L09** | "What is Article 11?" retrieves 11-178, 11-149, 11-221.1 — never the Article's own opening sections, because hybrid search has nothing to match in 11-101 "Creation of fund" | call `outline(11)`, see 11-101, read it |
| **L07** | passes, but only because the member's own figure drags §11-134 in regardless | keep passing, for the right reason |

L09 is the sharpest case in the suite: the most basic question anyone can ask
about an Article cannot reach that Article's opening sections. The `outline`
tool built in Phase 1 exists for it and has never had a caller.

Create `tests/test_llm_tools.py`:

```python
"""One model call that may ask for tools, parsed into something the loop can use.

Everything here is offline: the Azure client is replaced, because what is being
tested is the parsing, not the network. The one thing a live probe established
-- that this deployment returns `finish_reason: tool_calls` with well-formed
arguments -- is not something a unit test can or should assert.
"""

from __future__ import annotations

import pytest

from pension_chat.agent import llm


class _Fn:
    def __init__(self, name: str, arguments: str) -> None:
        self.name = name
        self.arguments = arguments


class _Call:
    def __init__(self, id: str, name: str, arguments: str) -> None:
        self.id = id
        self.type = "function"
        self.function = _Fn(name, arguments)


class _Message:
    def __init__(self, content=None, tool_calls=None) -> None:
        self.content = content
        self.tool_calls = tool_calls


class _Choice:
    def __init__(self, message, finish_reason) -> None:
        self.message = message
        self.finish_reason = finish_reason


class _Response:
    def __init__(self, message, finish_reason="stop") -> None:
        self.choices = [_Choice(message, finish_reason)]
        self.usage = None


def _client(response):
    class _Completions:
        async def create(self, **kwargs):
            _client.seen = kwargs
            return response

    class _Chat:
        completions = _Completions()

    class _Client:
        chat = _Chat()

        def with_options(self, **kwargs):
            return self

    return _Client()


async def test_a_tool_call_is_parsed_with_its_arguments(monkeypatch):
    response = _Response(
        _Message(tool_calls=[_Call("c1", "search_statute", '{"queries": ["early retirement"], "why": "x"}')]),
        finish_reason="tool_calls",
    )
    monkeypatch.setattr(llm, "get_llm", lambda: _client(response))

    turn = await llm.call_with_tools(node="t", messages=[], tools=[])

    assert len(turn.calls) == 1
    assert turn.calls[0].name == "search_statute"
    assert turn.calls[0].arguments == {"queries": ["early retirement"], "why": "x"}
    assert turn.calls[0].id == "c1"


async def test_no_tool_calls_means_the_model_is_done(monkeypatch):
    monkeypatch.setattr(llm, "get_llm", lambda: _client(_Response(_Message(content="Here is the answer."))))

    turn = await llm.call_with_tools(node="t", messages=[], tools=[])

    assert turn.calls == ()
    assert turn.content == "Here is the answer."


async def test_malformed_arguments_do_not_kill_the_turn(monkeypatch):
    """A model that sends broken JSON has still told you which tool it wants.

    Raising here would end the conversation over a recoverable mistake; the
    loop can run the tool with nothing and let it report what it needed.
    """
    response = _Response(
        _Message(tool_calls=[_Call("c1", "search_statute", "{not json")]),
        finish_reason="tool_calls",
    )
    monkeypatch.setattr(llm, "get_llm", lambda: _client(response))

    turn = await llm.call_with_tools(node="t", messages=[], tools=[])

    assert turn.calls[0].name == "search_statute"
    assert turn.calls[0].arguments == {}


async def test_the_assistant_message_comes_back_appendable(monkeypatch):
    """The API rejects a `role: "tool"` result whose call is not in the history."""
    response = _Response(
        _Message(tool_calls=[_Call("c1", "outline", '{"article": 11}')]),
        finish_reason="tool_calls",
    )
    monkeypatch.setattr(llm, "get_llm", lambda: _client(response))

    turn = await llm.call_with_tools(node="t", messages=[], tools=[])

    assert turn.raw_message["role"] == "assistant"
    assert turn.raw_message["tool_calls"][0]["id"] == "c1"
    assert turn.raw_message["tool_calls"][0]["function"]["name"] == "outline"
```

- [ ] **Step 3: Implement**

In `llm.py`, beside `complete()`, sharing its retry shape (`_RETRYABLE` only;
a 400 is a bug and is raised immediately):

```python
@dataclass(frozen=True)
class ToolCall:
    """One tool the model asked for, with its arguments already parsed."""

    id: str
    name: str
    arguments: dict[str, Any]


@dataclass(frozen=True)
class ToolTurn:
    """What one model call came back with: tools to run, or an answer."""

    calls: tuple[ToolCall, ...]
    content: str
    raw_message: dict[str, Any]

    @property
    def done(self) -> bool:
        return not self.calls


async def call_with_tools(
    *,
    node: str,
    messages: list[dict],
    tools: list[dict],
    usage: TokenUsage | None = None,
    reasoning_effort: str = "none",
    attempts: int = 2,
    timeout: float | None = None,
) -> ToolTurn:
    """One completion that may ask for tools.

    Broken arguments come back as an empty dict rather than an exception: the
    model has still said which tool it wants, and ending a member's turn over
    recoverable JSON is worse than running the tool with nothing and letting it
    report what it needed.
    """
```

Body mirrors `complete()`: same kwargs, plus `tools` and
`tool_choice="auto"` when `tools` is non-empty. Build `raw_message` by hand
rather than serialising the SDK object, so the history holds plain dicts.

### Task 2: The four retrieval tools

**Files:**
- Create: `src/pension_chat/agent/tools.py`
- Test: `tests/test_tools.py` (create)

**Interfaces:**
- Consumes: `retrieval.retrieve`, `retrieval.fetch_sections`, `corpus.outline`, `corpus.related_sections` — all existing.
- Produces:
  ```python
  RETRIEVAL_TOOLS: list[dict]          # OpenAI schemas
  async def run_tool(name: str, arguments: dict, state: dict) -> tuple[str, dict]
  ```
  Returns `(text_for_the_model, state_update)`. The state update is merged into
  `PensionAgentState` by the loop, which is how `retrieved_sections` accumulates
  and why nothing downstream changes.

Two contracts matter more than the schemas:

**`search_statute` returns its own scores plainly.** The known weakness of a
self-grading loop is a model deciding "good enough" and answering. Naming the
best score in the result text makes a weak search visible rather than inferred.

**Every tool answers, even when it fails.** An unknown section, an empty
outline, a malformed argument — each returns text saying so. A tool that raises
ends the member's turn; a tool that explains lets the model try something else.

### Task 3: The loop

**Files:**
- Create: `src/pension_chat/agent/loop.py`
- Test: `tests/test_loop.py` (create)

**Interfaces:**
- Consumes: `llm.call_with_tools`, `tools.RETRIEVAL_TOOLS`, `tools.run_tool`.
- Produces: `async def investigate(state: PensionAgentState) -> dict` — runs to exhaustion or until the model stops calling tools, and returns a state update including `loop_messages` (the history, for `compose`) and the accumulated tool state.

**The budget is per resource, not per iteration** (spec §2.1): 20 tool calls,
6 searches, 3 derivations, 12 computations, 90s wall clock. In 3a only the first
two bite. **Exhausting a sub-budget removes that tool and says why; it does not
end the turn** — a loop out of searches can still read a section it already
knows about.

**Evidence sufficiency** (spec §2.1): on exhaustion, compute the
cross-references named in the gathered evidence minus the sections actually
read, and hand the remainder to `compose` as a fact. `retrieval.RetrievedSection`
carries `referenced_sections`, and Phase 1's `corpus` has the full graph.

| Category | Pipeline | Loop |
|---|---|---|

| retrieval | 2/2 | 2/2 |

**Five of the seven routing/conversational losses are expected**: L08, L10, R03,
R04 and R07 all report "no calculation ran", and 3a deliberately has no
calculation tools. They are 3b's, and R03 is CRITICAL.

**Two are real and unresolved:**

1. **The loop cites sections it has not read.** L09 did it once with 11-124 seen
   in an outline; R05 did it with 11-160.1 seen inside another section's text,
   and the guardrail replaced the answer with the fallback. `ANSWER_SYSTEM`
   already forbids it ("A section number merely *mentioned inside* that text is
   not one you have read"), and `compose` now also names the readable set
   outright -- **and it still happens.** The guardrail is holding, so nothing
   false reaches a member, but an answer withdrawn is an answer lost. The next
   attempt should probably be structural rather than another instruction: the
   tools could strip or mark inline section references, so an unread number
   never appears in a citable-looking form.
2. **R02: survivor questions retrieve the wrong provisions.** Substantive answer,
   wrong sections, no 11-145.1 or 11-134.2. Same class as L05, which also fails
   on the pipeline -- so this is a retrieval-quality problem the loop has not
   fixed rather than one it caused.

### Recommended next step

Not 3b. Fix the unverified-citation defect first: it is the one failure mode
that costs a member a whole answer, it recurs across unrelated cases, and two
