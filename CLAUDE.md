# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An AI chatbot for the Illinois Pension Code (40 ILCS 5/) that answers member questions with cited statute text and, where applicable, deterministically-calculated benefit figures. Backend is FastAPI + LangGraph + Postgres + Azure OpenAI + Azure AI Search; frontend is Next.js. Full design rationale lives in `pension-chatbot-architecture-final-v5.3.md` — read it before making architectural changes, especially §7 (calculation engine) and §9 (agent graph).

## Commands

Backend uses `uv`. Frontend is a separate Node project in `frontend/`.

```bash
# Backend — install deps
uv sync --all-extras

# Run the API (dev)
uv run uvicorn pension_chat.main:app --reload

# Lint / type-check
uv run ruff check .
uv run mypy .

# Tests (none exist yet; pytest is configured to look in tests/)
uv run pytest
uv run pytest tests/path/test_file.py::test_name   # single test

# DB migrations (Alembic reads PG* vars from .env via alembic/env.py)
uv run alembic upgrade head
uv run alembic revision -m "description"           # migrations are hand-written (they include RLS policies), not autogenerated

# One-off data scripts
uv run python scripts/ingest_articles.py            # parse/chunk/embed statute text -> Azure AI Search
uv run python scripts/seed_synthetic_data.py         # seed synthetic employees for the pilot
```

```bash
# Frontend
cd frontend
npm run dev      # Next.js dev server (Turbopack)
npm run build
npm run lint
```

Config is env-driven via `pension_chat/config.py` (`pydantic-settings`, reads `.env`). Copy `.env.example` to `.env` and fill in Azure OpenAI, Azure AI Search, and Postgres (`PGHOST`/`PGUSER`/`PGPORT`/`PGDATABASE`/`PGPASSWORD`) credentials before running anything that touches the DB or LLM.

## Architecture

### The core split: LLM plans, code calculates

The central design rule (see architecture doc §1) is that the LLM agent plans, retrieves, and writes prose — but it **never performs authoritative arithmetic itself**. All benefit math runs through a deterministic interpreter. Keep this split intact when touching the agent or calculation code: don't let a node ask the model to "compute" a number that should come from the DSL interpreter.

The Pension Code is treated as three layers:
1. **Unstructured legal corpus** — statute text, chunked and indexed in Azure AI Search for hybrid retrieval (vector + BM25 + semantic ranker) and citation (`ingestion/`).
2. **Reusable calculation knowledge** — structured "recipes" the agent discovers from retrieved statute text and persists to `formula_registry` for reuse (`db/models.py::FormulaRegistry`).
3. **Deterministic execution layer** — `calculation/dsl_interpreter.py` executes a recipe's `rule_specification` JSON tree; `calculation/custom_handlers.py` handles cases too irregular for the declarative DSL.

A recipe's `rule_specification` is a JSON operation tree (`calculation/dsl_types.py::OperationNode`/`RuleSpecification`) built only from a fixed operation set (ADD/SUBTRACT/.../LOOKUP/CAPABILITY_REF, etc.) — this is intentionally not a general-purpose expression language, so no arbitrary code execution reaches the interpreter. `FormulaRegistry` rows carry a full lifecycle (`knowledge_status`: discovered → agent_derived → validated → approved → stale/retired) and an `execution_policy` (`no_execute` / `estimate` / `authoritative`) gating whether a recipe can actually run; `calculation/risk_assessor.py` assigns `risk_tier` from objective signals (topic, branch count, cross-article dependencies — never the model's self-assessment), and `calculation/validator.py` checks structural/evidence completeness before a recipe is allowed to execute.

### Agent graph (`agent/`)

`agent/graph.py::build_graph()` assembles a LangGraph `StateGraph` over `PensionAgentState` (`agent/state.py`, a `TypedDict` blackboard). Flow:

```
triage                                   (deterministic: scope, adversarial-instruction scan, section refs)
  ├─(out of scope / greeting)─> decline ─> END          (no model call, no DB call)
  └─> [plan_request ∥ fetch_employee_record]            (independent; run concurrently)
            └─> retrieve_policy                          (hybrid search, article-filtered, cross-references followed)
                  └─> resolve_recipes                    (registry lookup, else derive from statute)
                        ├─(no calculation)──────────────────────────┐
                        └─> resolve_inputs ─> validate_recipes ─> execute_calculations
                                                                     │
                                                              prepare_answer ─> END
```

**Node order encodes hard data dependencies** — `retrieve_policy` needs the member's Article number to filter on, `resolve_recipes` needs the retrieved text to derive from, and `resolve_inputs` needs the recipe to know which inputs exist. Only `plan_request` and `fetch_employee_record` are genuinely independent, and those two are the concurrent pair.

`prepare_answer` assembles the prompt but makes **no model call**. Answer generation lives outside the graph in `graph.py::run_agent_stream()`, which streams tokens to the client as they arrive and then runs post-generation verification. `run_agent()` is the non-streaming wrapper used by tests and `scripts/eval_agent.py`. State defaults live in one place, `state.py::initial_state()` — add a new state key there as well as to the TypedDict.

### Guardrails (`agent/guardrails.py`)

All deterministic Python; no model grades another model's output. Before generation: scope classification and detection of "apply my formula, skip the Code" instructions (which annotate the answer prompt rather than refusing). After generation: every cited section must be one that was retrieved, and every money/percentage figure must trace to a calculation result, the retrieved statute text, the member's record, or the member's own messages. A hard failure replaces the streamed answer via the SSE `replace` event.

### Evaluation

`scripts/eval_agent.py` runs the 16-case regression suite (the 12 from `test_questions.md` plus 4 safety cases) against the live index and model, reporting pass/fail, time-to-first-token, and token cost per turn. `uv run python scripts/eval_agent.py --help` for options. Unit tests in `tests/` cover the deterministic layers (facts, guardrails, DSL interpreter, validator) and need no network.

### API / streaming (`api/`)

FastAPI app assembled in `main.py`, routers registered there (`health`, `auth`, `sessions`, `admin`). Chat responses stream over SSE — `sessions.py::send_message` yields events via helpers in `sse/` (`sse_preamble`, `sse_status`, `sse_token`, `sse_done`, `sse_error`) as the agent graph progresses through planning/answering. Auth is JWT-based (`api/auth.py`, `python-jose`/`passlib`), issued on `/register`/`/login`; sessions can also be anonymous (`Session.employee_id` nullable, tracked instead by `session_token`).

### Database (`db/`, `alembic/`)

`db/models.py` is SQLAlchemy 2.0 ORM matching the architecture doc's §7.1 schema exactly — Alembic migrations should derive from these models, not the other way around. Key tables: `pension_articles` (one row per Article of the Code), `employees`/`employee_salary_history` (synthetic for the pilot — see `is_synthetic`), `sessions`/`session_messages` (chat + audit trail), `formula_registry` (the calculation knowledge registry described above).

Every query path goes through `db/session.py::get_db_session()`, which sets Postgres session variables (`app.current_employee_id`, `app.current_session_token`) via `SET LOCAL` before the query — these back **row-level security policies** enforced at the DB layer, so don't bypass this helper for user-scoped queries. `get_admin_session()` is the explicit unrestricted escape hatch for admin/system operations (`api/admin.py`) — use it deliberately, not as a default.

### Ingestion pipeline (`ingestion/`, `scripts/ingest_articles.py`)

`parser.py` → `chunker.py` → `embedder.py` → `indexer.py`, in that order, uploading to Azure AI Search and updating `pension_articles.ingestion_status`. `relevance_tagger.py` tags chunks for retrieval filtering. The pilot validates this pipeline end-to-end against Article 11 and Article 12 only (deliberately adjacent/confusable articles, per architecture doc §2) before scaling to the full ~20-article code — keep that two-article scope in mind when reasoning about what "should" be ingested/working at this stage.

### Frontend (`frontend/`)

Next.js 16 (App Router, Turbopack) + React 19 + Tailwind v4 + shadcn/base-ui components. `src/lib/api.ts` is the backend client; chat UI lives in `src/components/chat/` (`ChatInterface`, `ChatMessage`, `Sidebar`). No test setup currently.
