# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An AI chatbot for the Illinois Pension Code (40 ILCS 5/) that answers member questions with cited statute text and, where applicable, deterministically-calculated benefit figures. Backend is FastAPI + LangGraph + Postgres + Azure OpenAI + Azure AI Search; frontend is Next.js. Full design rationale lives in `pension-chatbot-architecture-final-v5.3.md` — read it before making architectural changes, especially §7 (calculation engine) and §9 (agent graph).

## Commands

Backend uses `uv`. Frontend is a separate Node project in `frontend/`.

```bash
# Backend — install deps
uv sync --all-extras

# Run the API (dev)
uv run uvicorn pension_chat.main:app --reload

# Lint / type-check
uv run ruff check .
uv run mypy .

# Tests (none exist yet; pytest is configured to look in tests/)
uv run pytest
uv run pytest tests/path/test_file.py::test_name   # single test

# DB migrations (Alembic reads PG* vars from .env via alembic/env.py)
uv run alembic upgrade head
uv run alembic revision -m "description"           # migrations are hand-written (they include RLS policies), not autogenerated

# One-off data scripts
uv run python scripts/ingest_articles.py            # parse/chunk/embed statute text -> Azure AI Search
uv run python scripts/seed_synthetic_data.py         # seed synthetic employees for the pilot
```

```bash
# Frontend
cd frontend
npm run dev      # Next.js dev server (Turbopack)
npm run build
npm run lint
```

Config is env-driven via `pension_chat/config.py` (`pydantic-settings`, reads `.env`). Copy `.env.example` to `.env` and fill in Azure OpenAI, Azure AI Search, and Postgres (`PGHOST`/`PGUSER`/`PGPORT`/`PGDATABASE`/`PGPASSWORD`) credentials before running anything that touches the DB or LLM.

## Architecture

### The core split: the model decides, code calculates

The central design rule (see architecture doc §1) is that the LLM agent decides, retrieves, and writes prose — but it **never performs authoritative arithmetic itself**. All benefit math runs through a deterministic interpreter. Keep this split intact when touching the agent or calculation code: don't ask the model to "compute" a number that should come from the DSL interpreter. The agent chooses *when* to compute, on what premise, and with which stated values; `compute_benefit` does the rest and it is the only way to a figure.

The corollary, learned expensively at cutover: **anything the model must not get wrong is enforced in code that reads the same state the guardrail reads.** A paragraph in a tool schema is a warning, not a mechanism — `stand_in_facts` said "only when the member asked" and was set when they had not; `find_provision` said "this does not put the text in front of you" and was cited anyway.

The Pension Code is treated as three layers:
1. **Unstructured legal corpus** — statute text, chunked and indexed in Azure AI Search for hybrid retrieval (vector + BM25 + semantic ranker) and citation (`ingestion/`).
2. **Reusable calculation knowledge** — structured "recipes" the agent discovers from retrieved statute text and persists to `formula_registry` for reuse (`db/models.py::FormulaRegistry`).
3. **Deterministic execution layer** — `calculation/dsl_interpreter.py` executes a recipe's `rule_specification` JSON tree; `calculation/custom_handlers.py` handles cases too irregular for the declarative DSL.

A recipe's `rule_specification` is a JSON operation tree (`calculation/dsl_types.py::OperationNode`/`RuleSpecification`) built only from a fixed operation set (ADD/SUBTRACT/.../LOOKUP/CAPABILITY_REF, etc.) — this is intentionally not a general-purpose expression language, so no arbitrary code execution reaches the interpreter. `FormulaRegistry` rows carry a full lifecycle (`knowledge_status`: discovered → agent_derived → validated → approved → stale/retired) and an `execution_policy` (`no_execute` / `estimate` / `authoritative`) gating whether a recipe can actually run; `calculation/risk_assessor.py` assigns `risk_tier` from objective signals (topic, branch count, cross-article dependencies — never the model's self-assessment), and `calculation/validator.py` checks structural/evidence completeness before a recipe is allowed to execute.

### Agent loop (`agent/`)

`agent/graph.py::build_loop_graph()` assembles a LangGraph `StateGraph` over `PensionAgentState` (`agent/state.py`, a `TypedDict` blackboard). Three nodes, where the pipeline it replaced at cutover had eleven:

```
triage                          (deterministic: deny list, greeting, adversarial scan, section refs)
  ├─(out of scope / greeting)─> decline ─> END    (no model call, no DB call)
  └─> fetch_employee_record                       (first, so the loop has the member from iteration one)
        └─> investigate                           (search, read, reconsider, compute — one mind, six tools)
              └─> compose                         (continues that same conversation into the answer) ─> END
```

**One mind, not two.** `compose` appends the style half of the answer prompt to the *investigation's own message history* rather than opening a fresh call. Handing a model that never saw the statute a pile of text and asking it to narrate is the split this design exists to remove: the model that read the section is the model that writes the sentence about it. It makes **no model call** itself — generation lives outside the graph in `graph.py::run_agent_stream()`, which streams tokens as they arrive and then runs post-generation verification. `run_agent()` is the non-streaming wrapper used by tests and `scripts/eval_agent.py`. State defaults live in one place, `state.py::initial_state()` — add a new state key there as well as to the TypedDict.

**The tools are in `agent/tools.py`**, each with a budget in `loop.BUDGETS` (20 calls or 90s total): `search_statute`, `get_section`, `outline`, `related_sections`, `compute_benefit`, `check_coverage`. A spent sub-budget removes that tool and says so rather than letting the model keep trying it. `compute_benefit` runs `resolve_recipes → resolve_inputs → validate_recipes → execute_calculations` in that order — a correctness constraint, not a convenience — so **the arithmetic stays exactly where it was**: the model chooses when to compute and on what premise, and never does the sum.

`find_provision` was offered for one day and withdrawn (`tools._WITHDRAWN_PROVISION_TOOLS`), and the reason is a design rule: **a tool that can be called *instead of reading* will be.** It named a provision with no text attached, so the model cited a section it had not read; and answering "which provision" felt like the hard part, so turns stopped there without computing. Schema prose did not stop either. The fix took the note's own prescription — provision and text together, where naming one cannot be an alternative to having read it — and made it **not a tool**: `_engine_provisions` asks `registry.recipes_for` (one query, no model call, the same `_reuse_rank` `lookup_recipe` uses, so the provision named is the one a later figure rests on), fetches the section's text, and runs *after* the tool loop has ended, where nothing can call it instead of computing. It answers "why that one rather than its neighbours" too, from the `alternatives_considered` the derivation recorded and every reuse reads back.

**What a loop must not be trusted to do for itself.** A loop that decides what to read as it reads has no retrieval filter, and *the filter is the determination*. Everything below is a thing the graph did structurally, ported into deterministic Python — each one found by a case failing, not by design:

- **It always searches.** A turn spending only `{outline, get_section}` has browsed, not looked: §11-134 is "Amount of annuity", §11-130 is "Annuities — Present employees and future entrants" which reads like the better match and is not, and 11-127 through 11-131 cite *nothing*, so following references cannot escape. If the model searched nothing, its own question is searched for it — **filtered** to the governing Article, the cross-cutting ones, and the Article this fund takes its benefits from where `funds.py` declares one (10 → 9). Unfiltered, that dropped a slice of the whole Code into the citable set and the model spent it on hedges ("Section 7-109, but I cannot establish…"). **A gap reported with another fund's section number on it is still another fund's law in an answer about this member.**
- **It completes the evidence.** An answer naming §11-216 without its text in front of it is citing from memory, and verification rejects it. The most-leaned-on unread cross-references are fetched before `compose`.
- **It re-reads the provision the conversation settled on**, ungated by the budget — a turn that spent everything is the one most likely to have drifted. And `compose` *names* it (`_settled_provision`): reading it is necessary and not sufficient, which G30 settled by failing with §11-134 sitting in its own retrieved sections.
- **A premise confines what the answer may rest on.** Under a supposition naming an Article, the evidence is that Article and the cross-cutting ones; the rest was investigation, and `set_aside_sections` tells `compose` so.

**Three deterministic resolutions run before any model sees the turn** (`loop.investigate`), all three because a member who has said something must not have to say it twice: `_bind_open_question` settles a coverage question they just answered, `_leave_hypothetical` releases a supposition they stepped out of, and coverage falls back to the record when nothing has established it.

**`compose`'s blocks are facts, never stances** — each rendered by code reading the same state key the guardrail reads, so each costs nothing on a turn where that state is empty: `_worked_from` (the provision this turn's figure came from), `_settled_provision` (the one the conversation rests on, when no figure was worked), `_cliff_ahead` (a boundary the member is walking towards, priced by the same interpreter as their own figure), `_assumed` (values nobody supplied), `_confined_to_premise`'s set-aside note, and the borrowed-benefits bridge. **The block has to be where the decision is made:** the same fact sitting in the middle of the tool history does not reach the model writing the sentence.


### Coverage: the record is a prior, not an oracle (`agent/coverage.py`)

Which Article covers a member decides the retrieval filter, which decides the recipe, which decides the figure — and it used to be read straight off `employees.article_number` with no way to be contradicted. A member who wrote "i am a park employee" was told "As a park employee **covered by Article 11**…", welding their description to their record and asserting a connection the Code does not make (park employees are generally Article 12).

So a self-description is evidence, checked against the Code's own coverage sections rather than assumed. **Coverage is a tool the model calls (`check_coverage`), not a stage that runs** — the model reading the question knows a supposition when it sees one, and catches self-descriptions no word list survives. `classify_self_reference` reads which of three acts the member performed, and each is a distinct bug when handled as another:

| the member writes | act | behaviour |
|---|---|---|
| "I am a park employee" | **asserted** | check it against the corpus; ask on conflict |
| "if I were a park employee" | **stipulated** | adopt the premise, never ask, hold it across turns |
| "I think I'm a park employee" | **doubted** | *they* are unsure — always ask |

What the regex still decides is narrower and load-bearing: **a question is put to the member, so the member must have spoken.** `check_coverage` may raise a clarification only on a turn where `classify_self_reference` finds the member actually describing themselves; otherwise the verdict says which Article the law belongs to and asks nobody anything. "An employee is covered by Article 12 — what provisions should the system consider?" is a question about the law, and answering it "Which employer pays you?" is the failure that guard exists for.

`retrieve_coverage()` is the **only query in the system that is deliberately not article-filtered** (the question being asked *is* which Article), searching sections tagged `coverage_rule` by the ingestion tagger. `assess()` does the semantic work — no keyword table survives "a worker who works at the park" — but every candidate must name a section that was actually retrieved, or it is dropped; `adjudicate()` then decides in pure Python, and the record wins unless a *better-supported* Article outranks it. `bind_reply()` makes an answer stick, durably: without it a question is worse than none.

Two rules that are easy to get backwards. **A conflict in a routing field (`article_number`, `employment_status`) is a question; a conflict in a value (salary, service) stays an override-with-note** via the existing `input_overrides` path. And **a figure is computable exactly when no input is borrowed from a record filed under another Article** — enforced by starving record-derived facts in `resolve_inputs`, so everything becomes a missing input rather than a plausible wrong number. `_available_facts` is the single source of that rule and `loop._context` reads it too, so the member's own age and service do not reach the *prompt* under a supposition either — a model handed a figure reaches for it, which is how the first hypothetical answer set out Article 12's formula and then ran it on an Article 11 salary.

The one way out is the member offering their own values, and the invitation is **corroborated, not trusted**: `compute_benefit`'s `stand_in_facts` means "they asked for their salary and service to be used under the supposed job", the model decides whether they did, and `tools._invited_stand_ins` checks the words are really in their message or in the premise they set up. Left to schema prose, the flag got set on "if I were a park employee, how would my pension be calculated?" and quoted a whole Article 11 salary history through Article 12's formula.

The clarification budget (`config.clarification_budget`, default 3) is enforced: at the cap the agent proceeds on the record and says what it assumed. The fast exit matters as much as the feature — a turn where nobody described themselves costs no search and no model call.

### Guardrails (`agent/guardrails.py`)

All deterministic Python; no model grades another model's output. Before generation: scope classification and detection of "apply my formula, skip the Code" instructions (which annotate the answer prompt rather than refusing). After generation: every cited section must be one that was retrieved, and every money/percentage figure must trace to a calculation result, the retrieved statute text, the member's record, or the member's own messages. A hard failure replaces the streamed answer via the SSE `replace` event.

Coverage is checked the same way, and in both directions. An answer may state which Article covers the member only when `coverage.basis` is `member_confirmed` or `statutory_match` — *attributing* it ("your record places you in Article 11") is always fine, since the distinction being policed is a claim about the law versus a statement about the file. Conversely, an answer to a stipulated premise must stay visibly conditional: answering "if I were a park employee" in the plain indicative tells a member they are in a fund they only asked about. Quoted spans are stripped before both checks — an answer explaining its own earlier mistake has to be able to repeat it.

### Evaluation

`scripts/eval_agent.py` runs the benchmark in `evals/*.yaml` against the live index and model. **A case is a conversation on one thread**, with per-turn expectations — the graph is checkpointed, so turn two resumes from what turn one established rather than being handed a transcript to re-read. Reports per-category pass rates, time-to-first-token and tokens per turn, plus a CRITICAL block that fails the run whatever the overall score says. `--category <name>` runs one family; `--help` for the rest. **Check a structure, not a substring, wherever the behaviour produces one**: `answers_from_article` reads the citations the verifier accepted and the provision the figure was worked from, and `cites_outside` is its opposite for the question that asks for other Articles to be named. Its predecessor `article_only` policed *retrieval*, which was the same question only for an agent whose Article filter was its determination; it went with the pipeline. `evals/fund_smoke.yaml` is one case per member fund, run as its standard persona (seeded by `seed_synthetic_data.py`): coverage must resolve to the fund's own Article, and a figure must rest on that Article's sections or the turn must name what is missing (`fund_figure`). The failure it exists for is a borrowed formula — a police or fire fund given a figure from another Article's recipe, with a real citation on it. `scripts/replay_coverage.py` replays the conversation that motivated the coverage layer, printing the per-turn state beside each answer.

Unit tests in `tests/` cover the deterministic layers (facts, guardrails, coverage, DSL interpreter, validator) and need no network. One of them guards a *bug class* rather than a behaviour, by parsing the alternatives out of a regex and requiring every one to have a worked example — `test_coverage.py` for the act governors. That pattern was written for a planner's signal regex, where three alternatives were dead for as long as they had existed and reading the regex did not reveal it; the same guard later caught a coverage governor that no frame could ever reach. The planner is gone, and the lesson generalised instead: **a regex that decides what a member meant cannot be made safe by testing it harder** — so the surviving ones only accuse, supply data, or check provenance.

**Deleting a test is a decision about a behaviour, not about a file.** At cutover the pipeline's tests were triaged one at a time, and the two that were *repointed* rather than deleted — `test_coverage.py`'s pair, from `prepare_answer` to `loop._context` — failed on the new target and were right to: the loop was handing a supposition the member's own age and service, and calling the supposed Article the one their record placed them in. A test whose subject moved is worth more than a test whose subject died.

### API / streaming (`api/`)

FastAPI app assembled in `main.py`, routers registered there (`health`, `auth`, `sessions`, `sections`, `profiles`, `admin`). Chat responses stream over SSE — `sessions.py::send_message` yields events via helpers in `sse/` (`sse_preamble`, `sse_status`, `sse_token`, `sse_replace`, `sse_done`, `sse_error`) as the agent graph progresses through planning/answering. Auth is JWT-based (`api/auth.py`, `python-jose`/`passlib`).

`done` carries the verified citations, the audit trail in `tool_calls`, and the conversation's scenarios. The trail also holds the **calculation card** (`agent/card.py`): the first successful figure, its section, whether it is an estimate, each input with its origin, and the worked steps and assumptions exactly as the answer's own blocks rendered them — carried, not re-derived, and **withheld when verification replaced the answer**, because the figures beside an unverified answer are unverified too. An input's origin is recorded by `resolve_inputs` as it resolves (`input_sources`), never reconstructed from the worksheet, which holds a stated value only when the model also reported a revision. **Scenarios** (`graph.active_scenarios`) are what the member built — not the "if you retire now" figure every calculation files, and not the superseded copies a correction leaves; `GET`/`DELETE /sessions/{id}/scenarios` read and forget them in the checkpoint, and since `scenario_set` merges, forgetting one is `CLEAR` then writing back the rest. Statute text for the evidence drawer is `GET /sections/{id}`: public, and its id is gated by a regex because `fetch_sections` interpolates ids into an OData filter.

**Stop is a disconnect, and nothing after the stream's loop runs on one.** The disconnect cancels the request's anyio scope, and `CancelledError`/`GeneratorExit` are BaseExceptions `except Exception` never sees — so the answer used to vanish while the question, written on its own task, survived. `event_stream`'s `finally` keeps what was streamed inside a shielded cancel scope, marked `{"type": "stopped"}` with `guardrail_passed` NULL. The same cancellation used to leave a closed connection in the pool for the next request (a 500, "connection is closed"): the session helpers shield their rollback and close, and a pool `checkout` listener (`db/session.py::discard_closed_connection`) refuses a connection asyncpg already knows is closed — at no network cost, unlike `pool_pre_ping`.

**Two ways in, and the anonymous one is the front door.** `Session.employee_id` is nullable and anonymous sessions are scoped by `session_token` (the `X-Session-Token` header, its own RLS predicate in migration 003, and `BASIS_UNRESOLVED` through the agent). Most of what this assistant answers well needs no record, and a member who states their own age and service gets a figure whose every input traces to their own message — better provenance than a record would give. `GET /sessions` returns `[]` without an identity by design (architecture doc §8): one conversation per visit, restored on reload from the stored token, no cross-visit history, because there is no identity to authenticate a list against. Cross-visit history is what an account is for.

**Signing up means picking a member, not authoring one** (`personas.py`, `POST /auth/signup`). Every determination rests on the record being evidence *independent* of what the member says — `coverage.py` treats the record and the member's word as two voices, `guardrails.py` traces figures to "the member's record" and "the member's own messages" as separate provenance classes — and a self-authored record collapses those into one voice agreeing with itself. Personas are authored here, so the record stays a second voice and "your record shows" stays honest. Values are editable within **relational** bounds (`personas.validate`), because independent per-field ranges still admit someone hired before they were born. **Editing the salary rescales the salary history**, since the annuity comes from `final_average_salary` over four consecutive years and not from current pay — leave them independent and the pension does not move when the member changes their pay. Tier is never asked: `derive_tier` reads it off the hire date, the `CHECK (tier IN (1,2))` would accept a wrong answer silently, and tier keys the recipe registry. `personas.py` is also what `seed_synthetic_data.py` and `eval_agent.py` read, with fixed ids — both previously pinned ids that `gen_random_uuid()` happened to produce, so a re-seed bound those cases to nothing without failing.

**One account, many profiles** (migration `005_accounts`, `api/profiles.py`). A profile is an `employees` row with an `account_id`; the token names the account (`typ: "account"` — an older token is a clean 401), and which profile a request acts as is the conversation's own, `sessions.employee_id`. That is why every employee-keyed policy, the checkpointer, `fetch_employee_record` and the evals did not change. Account-level work — `GET /me`, creating, editing and choosing profiles, listing an account's conversations, a signed-in `POST /sessions` (one `INSERT … SELECT` that checks ownership and falls back to the primary profile) — runs through `get_db_session(account_id=…)` under three account policies, so the database, not the handler, keeps one account out of another's profiles. **Every member fund has a profile** (Phase 3b, `funds.py`): one standard persona per fund for Articles 2–19 beside the Article 11 and 12 presets. `funds.py` owns per-Article config — the employer group and member label the picker leads with (members know their employer, not their Article), the fields a profile shows with that Article's bounds (`personas.validate` reads them; the frontend renders the form from them), and a `support_level`. **Support level is a claim to members, so it is set in config and never inferred**: 5, 6, 7, 8, 9, 11 and 12 are `checked`; every other fund is `experimental` — statute answers sound, a figure possibly missing or not yet checked — and the preset, profile menu and calculation card say so. A fund is promoted when its `evals/fund_smoke.yaml` case passes *with a figure worked by hand against its statute*: the case checks a figure's law, not its value, so a pass by naming missing inputs (13, 15) or with a figure the statute does not pay (19 — the agent reads §19-109's "attains an age of 65" against the member's age today rather than at retirement) is not enough. Each working standard member is past their own fund's Tier 1 retirement threshold as the Article states it (`tests/test_funds.py` holds the thresholds and sections), so the smoke question — "what if I retired at the end of this year?" — tests the fund's formula rather than drawing an honest "not yet". **A fund's own fields** (`Fund.extra_fields`) live in `employees.extra_facts` (JSONB, migration 006) and reach the engine through `build_member_facts`, published under every name in their `facts.ALIAS_GROUPS` entry. So far: whether a state employee is covered by Social Security, which sets §14-108's accrual rate; and police and fire outside Chicago label their salary "Salary attached to rank" (§3-111, §4-109), aliased as `salary_attached_to_rank`. A field is added only when a recipe reads it, and `personas.validate` refuses any name the profile's fund does not declare — that JSON arrives from an open endpoint. `persona_from_row` lets an edit apply the same bounds as signup. **Switching profile starts a new chat, and a conversation keeps the record it loaded on its first turn** (`pinned_record`, a durable key): an edit changes new chats, not one whose earlier answers rest on the old facts, and later turns skip a database round trip.

`/register` is the separate, narrower path for claiming one of the two pre-seeded pilot members: it matches only rows with a NULL password and no account, and creates an account over the row. `require_admin` guards everything in `api/admin.py` and reads `accounts.is_admin` per request rather than from a token claim, since a claim in a 24-hour token cannot be revoked — `require_auth` only asks whether somebody is signed in, which is not the question `POST /formulas/{id}/promote` needs to ask.

### Database (`db/`, `alembic/`)

`db/models.py` is SQLAlchemy 2.0 ORM matching the architecture doc's §7.1 schema exactly — Alembic migrations should derive from these models, not the other way around. Key tables: `pension_articles` (one row per Article of the Code), `accounts` (sign-in: one per person, owning any number of `employees` rows as profiles — migration 005), `employees`/`employee_salary_history` (synthetic for the pilot — see `is_synthetic`), `sessions`/`session_messages` (chat + audit trail), `formula_registry` (the calculation knowledge registry described above).

Every query path goes through `db/session.py::get_db_session()`, which sets Postgres session variables (`app.current_employee_id`, `app.current_session_token`, `app.current_account_id`) in one transaction-local `set_config` statement before the query — these back **row-level security policies** enforced at the DB layer, so don't bypass this helper for user-scoped queries. `get_admin_session()` is the explicit unrestricted escape hatch for admin/system operations (`api/admin.py`) — use it deliberately, not as a default.

### Ingestion pipeline (`ingestion/`, `scripts/ingest_articles.py`)

`parser.py` → `chunker.py` → `embedder.py` → `indexer.py`, in that order, uploading to Azure AI Search and updating `pension_articles.ingestion_status`. `relevance_tagger.py` tags chunks for retrieval filtering.

**Ingested: every Article with an integer number — 1 through 24** (`target_articles` in `scripts/ingest_articles.py`), 4,766 indexed documents. 11 and 12 remain the pilot pair, deliberately adjacent and confusable (architecture doc §2); 8 and 9 are the two funds nearest them. Widening past those six made coverage a twenty-way choice, and it held: `i am a park employee` still resolves to Article 12 on §12-118 alone, and Article 10 — the Forest Preserve District fund, the nearest new competitor — does not even surface as a candidate, because `assess()` drops any candidate that does not name a section actually retrieved and the Forest Preserve text says "forest preserve district", not "park".

**Not ingested: Articles 1A, 22A, 22B and 22C.** They parse to *zero* sections — the section-header pattern anchors the article on `(\d+)`, so `(40 ILCS 5/22A-101)` matches nothing — and widening it alone would not help, because `pension_articles.article_number` is a `SmallInteger` primary key with nowhere to put "22A". Both would have to change together. They are named in `UNSUPPORTED_ARTICLES` and skipped loudly, and an Article that parses to nothing now logs an error and stays at `validating` rather than being recorded as ingested over an empty index.

**1 and 20 have no members of their own but govern everyone's** — §1-160 is Tier 2, Article 20 is the Reciprocal Act (`retrieval.py::CROSS_CUTTING_ARTICLES`). That one fact has three consequences, and they are easy to get backwards:

- **They are never a coverage destination.** §20-104's "any person in the service of an employer" out-competes the funds on almost any self-description, so `coverage.py::NON_MEMBERSHIP_ARTICLES` drops them as candidates. Nobody is an Article 20 member; they are an Article 11 member with reciprocal service. That set is a *superset* of `CROSS_CUTTING_ARTICLES`, not an alias for it — the two only look the same at six Articles. Cross-cutting asks whether an Article governs this member alongside their own, which earns 1 and 20 a retrieval query of their own; non-membership asks whether a person could be a member at all, and the Code's administrative Articles (21 Social Security Enabling Act, 22 Miscellaneous Collateral Provisions, 23 Purpose–Savings–Repeal, 24 Deferred Compensation) fail that without being cross-cutting in the retrieval sense. Article 19 deliberately stays a destination: a closed fund is still a fund somebody belongs to.
- **They are not in the default search filter.** `fetch_sections` is unfiltered on every path, so a section the question names or the retrieved text cross-references already resolves whatever Article it lives in — that is where reachability comes from. Adding them to the filter instead put 309 more documents into every member's search and pushed §11-134 and §11-215 out of the top sections on cases that had been citing them. Still uncovered: a question *about* Tier 2 that names no section and whose best Article 11 hits don't cross-reference §1-160; pin it for Tier 2 members the way `coverage_sections` pins, rather than widening.
- **Naming one *adds* to the filter rather than moving it, and gets its own query.** Naming a fund Article moves the filter and means "read someone else's law"; naming a cross-cutting one must not, since it governs this member. And it needs a separate retrieval: Article 11 has 294 indexed subsections to Article 20's 35, so in a shared filter rank fusion returned three "Early retirement incentive" sections and, from the whole Reciprocal Act, its "Short title". `_ARTICLE_BY_NAME` also matches Article 20 by title, restricted to cross-cutting Articles on purpose — a fund Article matched by name would let "I am a park employee" bypass the coverage determination entirely, which is the exact bug that layer exists to prevent.

Three ways ILGA's own formatting silently loses or corrupts a section, all three live in the corpus and all three covered by `tests/test_ingestion.py`. **A section printed more than once under one header**, each copy marked `(Text of Section ...)` — text a court has struck beside text that stands (dropped), or concurrent/pending amendments nobody has reconciled (kept and labelled, since choosing between them is a reading of the law). **A letter-suffixed section id** (§1-113.4a) the header pattern did not match, so the section was never opened and its text was appended to §1-113.4 above it. **A section that letters two lists** (§9-219 enumerates service, then enumerates it again), whose repeated `(a)` overwrote the first. All three failed the same way — uploading merges by key, so a collision is not an error, just a section quietly short a subsection — which is why `test_ingestion.py` asserts key uniqueness across every article file, and why `indexer.py::prune_stale_records` deletes what a re-ingestion stopped emitting. Re-ingest after any parser change: keys move, and the old documents stay searchable otherwise.

Known and deliberately not fixed here: `embedder.py` truncates at `content[:8191]` **characters** where the model's limit is 8191 *tokens*, so roughly the last three-quarters of a long subsection is missing from its vector (not from its indexed text). It costs recall on §1-160-sized subsections.

### Frontend (`frontend/`)

Next.js 16 (App Router, Turbopack) + React 19 + Tailwind v4 + shadcn/base-ui components. `src/lib/api.ts` is the backend client and the one place that knows which principal this browser is (`credentialHeaders`, `auth`, `anonymousSession`). Chat UI lives in `src/components/chat/` — `ChatInterface` holds state and streaming; `ChatMessage`, `Composer`, `EmptyState`, `Sidebar`, `ChatHeader`, `CalculationCard`, `ScenarioChips`, and a `Drawer` with the evidence and calculation panels present it — and profile UI in `src/components/profile/` (`ProfileMenu`, `ProfilePanel`, `NewProfilePanel`, `SupportBadge`, plus `ProfileFields` — rendered from the fund's `fields` — and `PresetPicker` — search, then employer groups, via `lib/funds.ts` — which signup shares), with `app/signup` and `app/login` beside the chat at `app/page.tsx`. Pure logic lives in `src/lib/` and is tested with `npm test` — Node's own runner, since Node 22.18 strips types; tests import `./x.ts` with its extension, which `allowImportingTsExtensions` lets `next build` type-check. `npm run build` type-checks; `npm run lint` sits at 2 warnings, 0 errors.

**One design system, in the `globals.css` tokens** ("Civic calm — statute & seal", spec §3). Components use semantic utilities only: no raw palette classes, gradients or blur — a grep over `src/app` and `src/components/{chat,profile}` for them should come back empty. Navy is the one working accent; brass marks identity (the § seal) and place (the active conversation) and nothing else; the serif is reserved for statute text, so the typeface says when the Code is speaking rather than the assistant.

Two things here are easy to reintroduce. Send credential headers **only** when there is a credential: `Authorization: Bearer ${token}` with no token sends the literal string `"Bearer null"`, which is a token as far as the header is concerned, fails to decode and 401s — that is why anonymous chat did not work the first time it was reachable. And every `localStorage` access is wrapped: a private window or a browser set to block site data *throws* rather than returning null, and one throw during render takes the page down.
